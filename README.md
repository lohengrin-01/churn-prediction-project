## Overview

Customer churn occurs when a customer stops using a company's service. For a subscription-based telecom business, estimating churn risk can help a retention team prioritize outreach and investigate factors associated with customer departures.

The goal of this project is to build a **binary classification model** that estimates the probability of churn from customer attributes, then make that prediction accessible through an HTTP API.

**What this project covers:**

- Exploring customer data and relationships with churn.
- Preparing numerical and categorical features for machine learning.
- Training a logistic regression classifier and interpreting predicted probabilities.
- Evaluating classification performance using the concepts from ML Zoomcamp.
- Saving the trained preprocessing/model pipeline for inference.
- Serving predictions with **FastAPI**, validating requests with **Pydantic**, and packaging the application with **Docker**.

### Problem formulation

- **Task:** Binary classification.
- **Target:** Whether a customer churns (`1`) or stays (`0`).
- **Inputs:** Customer demographics, subscription details, tenure, billing information, and service usage indicators.
- **Output:** A churn probability between `0` and `1`, plus a Boolean classification.
- **Classification threshold:** `0.50` in the API implementation.

### Model and evaluation

The guided classification exercise uses **logistic regression**. Customer characteristics are transformed into model-ready features, including encoding categorical variables, and the saved scikit-learn pipeline is reused at prediction time.

For churn classification, **ROC-AUC, precision, recall, F1 score, and the confusion matrix** are useful evaluation tools. Accuracy alone can be misleading if churners and non-churners are unevenly represented. The choice of threshold also depends on the relative business cost of missed churners versus unnecessary retention outreach.

> **Results note:** This README intentionally does not report a numeric validation/test score because a final, verified metric has not been provided here. Consult the experiment notebook for recorded results before adding performance claims.

## API

The API is implemented in `predict.py` with FastAPI and Pydantic. It loads the serialized model from `churn_pipeline.pkl` and exposes a prediction endpoint.

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/predict` | Returns churn probability and a Boolean churn prediction. |
| `GET` | `/docs` | Interactive Swagger UI, generated by FastAPI. |
| `GET` | `/openapi.json` | OpenAPI specification, generated by FastAPI. |

### Example request

Start the service, then send a request to `http://localhost:9696/predict`:

```bash
curl -X POST "http://localhost:9696/predict" \
  -H "Content-Type: application/json" \
  -d '{
    "gender": "female",
    "seniorcitizen": 0,
    "partner": "yes",
    "dependents": "no",
    "tenure": 32,
    "phoneservice": "yes",
    "multiplelines": "yes",
    "internetservice": "fiber_optic",
    "onlinesecurity": "no",
    "onlinebackup": "yes",
    "deviceprotection": "no",
    "techsupport": "no",
    "streamingtv": "yes",
    "streamingmovies": "yes",
    "contract": "month-to-month",
    "paperlessbilling": "yes",
    "paymentmethod": "electronic_check",
    "monthlycharges": 93.95,
    "totalcharges": 2861.45
  }'
```

**Response format** (values below are illustrative, not measured model output):

```json
{
  "churn_probability": 0.73,
  "churn": true
}
```

The `churn` field is `true` when `churn_probability >= 0.5`.

**Input validation:** The Pydantic schema accepts specific categorical strings (for example, `fiber_optic`, `month-to-month`, and `electronic_check`) and checks numerical bounds. Invalid values return an HTTP `422` validation error. Use the interactive `/docs` page to inspect the current request schema.

## Run locally

### Option 1: Docker

From the project directory, with Docker installed and the model artifact available:

```bash
docker build -t churn-prediction .
docker run --rm -p 9696:9696 churn-prediction
```

Visit **http://localhost:9696/docs** to test the API from your browser.

### Option 2: uv

If working in the project's `uv`-managed environment:

```bash
uv sync
uv run uvicorn predict:app --host 0.0.0.0 --port 9696
```

The API expects `churn_pipeline.pkl` to be accessible at the path configured in `predict.py`.

## What I learned

This guided project helped me connect the core stages of a machine learning workflow: **data preparation → model training → evaluation → model serialization → API inference → containerization**.

In particular, it provided hands-on practice with:

- Interpreting a churn probability rather than only a class label.
- Keeping preprocessing consistent between training and inference.
- Designing typed prediction requests and validating them with Pydantic.
- Exposing a scikit-learn model through a REST API.
- Running an inference service inside a Docker container.

## Limitations and next steps

This is a **learning project**, not an operational retention system. A real-world implementation would require additional work, including evaluation against business-defined costs, data quality checks, security and authentication, monitoring, retraining, and testing on representative production data.

Potential improvements include automated API tests, reproducible training commands, explicit versioning of model artifacts, and deployment to a managed cloud service.
